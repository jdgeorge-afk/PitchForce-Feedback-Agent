# Architecture

## Stack and why

| Concern | Choice | Reason |
|---|---|---|
| Language | Python 3.11+ | Strong libraries for documents (python-docx, ReportLab, openpyxl), media and AI SDKs; one language end to end. |
| Web | FastAPI + server-rendered Jinja templates + small vanilla JS | Operator-friendly pages without a front-end build step; JSON endpoints only where the browser needs them (chunked uploads, live job progress). |
| Database | SQLAlchemy 2 + Alembic. SQLite (WAL) locally, PostgreSQL in production | Zero-setup local runs; the same models and migrations work on PostgreSQL. |
| Storage | Private local directory behind authorized routes (`pitchforce/storage.py`) | Nothing is served statically. Keys are generated by the app, never taken from user filenames. An S3-compatible backend can implement the same small interface. |
| Background jobs | Database-backed durable queue with leases (`pitchforce/jobs/`) | No extra service to run; survives restarts; jobs are visible in the UI. A separate **worker process** does all media/analysis/export work. |
| Media | FFmpeg (bundled via `imageio-ffmpeg`, or system FFmpeg) | Frame-accurate H.264/AAC clips; probing and validation. |
| AI | Provider abstraction: `offline` (deterministic rules) or `anthropic` (Claude, JSON-schema structured outputs) | Works without credentials; AI output is always validated against the source. |
| Auth | Email + password (scrypt), signed HTTP-only session cookie, CSRF tokens, per-event access checks | Suitable for a privately deployed business app. |

A modular monolith: one codebase, two processes (web and worker), one database, private storage. No microservices.

## Processes

```
Browser ──HTTPS──> web (FastAPI)            worker (python -m pitchforce worker)
                     │  pages, uploads (8 MB      │  claims jobs (conditional UPDATE + lease)
                     │  resumable chunks), API    │  ingest → analyze event → per-company jobs
                     ▼                            ▼  render clips → build packages → calendar
                  database  <───────────────────────>  private storage (sources, clips, artifacts)
```

The web process never does long media work. A large upload arrives in resumable chunks. Once the file is complete, an ingest job is queued.

## Package map

- `pitchforce/models.py` – all entities (see below). `migrations/` – Alembic.
- `pitchforce/parsing/` – transcripts (VTT/SRT/TXT, Zoom chat), CSV/XLSX reading with cell references, rosters, scores, poll exports (Zoom multi-section), documents and safe ZIP extraction.
- `pitchforce/services/` – ingest, identity matching, interest processing, scoring, clips and alignment, calendar, best practices, regeneration and staleness, inventory, retention, SSRF-safe fetching.
- `pitchforce/analysis/` – deterministic segmentation and extraction (`heuristics.py`), providers (`providers.py`), schemas, deterministic validation (`validate.py`), and the pipeline that persists results with provenance.
- `pitchforce/media/` – FFmpeg wrapper, transcript-to-video alignment, transcription adapter.
- `pitchforce/reports/` – section composition (`compose.py`), PDF/DOCX rendering, XLSX workbooks, packages.
- `pitchforce/jobs/` – queue, worker, handlers.
- `pitchforce/web/` – routes, templates, static assets.

## Data model (stable random IDs everywhere)

Event · SourceFile · Upload · Organization · Company · CompanyAlias · EntityRelationship · Person (presenter/judge/…) · PersonAlias · JudgeAttendance · SpeakerMapping · Utterance · CompanySegment · Question (with parts) · Feedback · Claim · Score · AnnouncedTotal · ScoreResult · PollLaunch · PollResponse · PollResponseChoice · ContactMatch · RecommendedAction · CalendarSession · CalendarRecommendation · BestPracticeVersion · AppSetting · AlignmentMap · Clip · ReportSection · Artifact · ShareLink · ReviewItem · ReviewDecision · ProcessingJob · AIUsage · AuditLog · User · EventAccess.

Names and emails are never identity keys. Original values (`*_raw`, `original` JSON, `original_row`) are kept next to normalized ones.

## Provenance and the "who said it" separation

Every derived record carries a `provenance` blob. It holds the source file ID and SHA-256, the transcript cue or row/cell reference, the speaker, the time interval, the excerpt copied verbatim from the source, the paraphrase, and the provider/model/prompt version. The origin is kept separate:

- `Claim.origin = founder_claim` – what the presenter said. Never marked verified automatically. Regulatory, efficacy, IP, funding and projection statements are flagged.
- Question / Feedback – what investors and moderators asked or said, attributed to the actual speaker.
- `system_inference` – e.g. theme grouping and suggested next actions.
- Operator decisions – aliases, relationships, attendance, review decisions and section edits, stored with user, time and scope (`event` or explicitly `global`).

## Analysis pipeline (staged, not one giant prompt)

1. **Ingest** each file: parse and keep raw values. Re-ingesting replaces derived rows but keeps operator overrides.
2. **Event segmentation** (`analyze_event`):
   - Detect presenters (speech concentrated in one window) and hosts (introduction cues).
   - Treat as judges the speakers active across several sessions.
   - Per presenter, find: intro, optional opening update, pitch, Q&A, feedback, score announcement, and award mentions.
   - Match each session to a roster company. Only exact names, confirmed aliases, or confirmed speaker mappings are certain. Everything else (fuzzy names, slot order) becomes a proposal with evidence and a review item.
3. **Per-company jobs** (failure-isolated): questions, feedback, founder claims, relationship cues, score result, clip candidate, calendar matches, report sections.
4. **AI path** (optional): the boundary, question, feedback and report-prose stages each use a small structured-output request (`output_config.format` JSON schema). Responses are then checked deterministically:
   - Utterance IDs must exist in the company's session.
   - The speaker is taken from the source.
   - Presenter lines cannot become questions; hosts become moderators.
   - Silent judges are decided by rule.
   - Numbers in the prose must appear in the evidence.

   Excerpts are always copied from the source. If anything fails, the offline result is kept and a note is recorded.

## Regeneration and staleness

- Each report section stores the hash of its inputs. Regeneration only updates sections whose inputs changed.
- An edited or approved section is never overwritten. It is marked **needs review**, and the new draft is kept for comparison.
- Artifacts store the hash of the package inputs (section text, clip render hash, interest rows). When the hash changes, downloads show **out of date**.
- Clip boundary changes mark the clip, the ZIP and the reports stale.

## Jobs: durability and idempotency

- **Idempotency:** a unique `idempotency_key` per job, and outputs are upserted by stable keys (sections per company/key; clips per company/variant/boundary hash; artifacts deduplicated by input hash and SHA-256).
- **Leases and heartbeat:** a crashed worker's job is reclaimed after the lease expires, counted as a new attempt.
- **Retries:** failures retry with backoff up to `JOB_MAX_ATTEMPTS`; `PermanentJobError` fails at once with an operator-readable message.
- **Ordering and cancellation:** dependencies use `payload.after` (rosters before the files that refer to them). Cancellation is checked at every progress update and while FFmpeg runs.
- **Costs:** AI and transcription cost estimates are recorded per job (`AIUsage`) using the configured prices.

## Security

- **Access:** authentication on every page; server-side event authorization on every event, company, media and artifact route (an inaccessible event returns 404 rather than 403, so IDs cannot be probed).
- **Requests and headers:** CSRF tokens on all state-changing requests; Content-Security-Policy and other security headers; login rate limiting.
- **Uploads and archives:**
  - Uploads are checked by type allowlist, magic bytes and size limits.
  - Storage keys are never derived from filenames.
  - ZIP extraction runs in memory with path-traversal, file-count, total-size and compression-ratio limits.
- **Content safety:** uploaded text is escaped in HTML and has control characters stripped in documents; spreadsheet cells are protected against formula injection.
- **Outbound requests:** fetching is limited to https allow-listed hosts, re-checked on every redirect, with public IPs only.
- **Secrets and sharing:** API keys stay server-side; nothing is emailed, messaged or shared automatically. Share links are random tokens stored as hashes, and they expire and can be revoked.
- **Provider disclosure:** the UI states which provider, if any, receives content.
- **Prompt-injection defense:** transcripts and documents are passed as data inside tagged blocks with a system instruction to ignore embedded instructions, and every output is validated against the source.
